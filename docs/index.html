Pull requests reviewed, fixed and unblocked by AI. You make the final call.

Three skills work together on your GitHub pull requests. One reviews. One fixes, with a test that fails first. One resolves merge conflicts. Each comment says who wrote it, and nothing merges without you.

Three skills, one pull request

Each skill does one job and says so in its report. They never call each other. They talk through the pull request itself.

  • pr-reviewer

    Reviews the diff. Read-only agents check the change from several angles, and every finding is checked before it is shown.

    Ends with one verdict: PASSED or BLOCKED.

  • pr-fixer

    Fixes what was found. Reproduces each finding, writes a test that fails first, fixes it, and posts a checklist with the evidence for every box.

    Ends with a closure comment, one line per finding.

  • pr-merge-fixer

    Resolves conflicts. Merges the base branch in, sorts each conflicted file by difficulty, and stops only when a decision really belongs to a person.

    Ends with a merge comment and a table of files.

How a pull request moves

The loop runs by itself, in the agent session you already use. It asks you only when the budget of automatic cycles is spent or a decision belongs to you.

  1. A pull request is opened or updated.
  2. If it conflicts with its base, the merge fixer resolves what it can.
  3. The reviewer checks the head and publishes one verdict, PASSED or BLOCKED.
  4. If BLOCKED, the fixer works the findings, then the reviewer runs again.
  5. Repeat until PASSED. When the cycle budget is spent, the question goes to you.
  6. On PASSED, you read the report and merge. The skills never merge.

Severity at a glance

Each finding has one of three labels. Only the first blocks a merge unless you change the setting.

LabelMeaningBlocks the merge?
CRITICALData loss, a security breach, an outage, or a broken rule the project declares non-negotiableAlways
WARNINGA likely bug in an edge case, or a missing test for new logicOnly if you set REVIEW_BLOCK_AT=warning
NOTEStyle, documentation, a questionNo

What the skills promise, and how to check it

  1. No GitHub Actions workflow calls a model. The review and the fix run in your own session, with your own authentication.
  2. Only comments from logins named in REVIEW_MARKER_AUTHORS count as reports. An edited comment never counts as a verdict.
  3. The skills never merge, approve, tag or release. The automatic reviewer never requests changes on GitHub.
  4. The scripts have a test suite that runs against a fake gh. Nothing touches GitHub while it runs.
